# 08 — Кросс-драйверная проверка коллаций

**What to build:** доказательство (не декларация), что сортировка ранга в БД побайтово совпадает с сортировкой в PHP на каждом реально поддерживаемом драйвере — самый рискованный пункт пакета, потому что SQLite зелёный независимо от того, что делает драйверная ветка макроса.

**Blocked by:** 03

**Status:** ready-for-agent

- [x] CI workflow: service-контейнеры MySQL, MariaDB, PostgreSQL — тестовый прогон запускается на каждом из них плюс SQLite (новый job `collation`, матрица по `db`, полный набор тестов на каждой ноге, а не только collation-тесты — дешёво и даёт защиту в глубину)
- [x] Тест сортировки: набор рангов вставляется через `FractionalRankGenerator` напрямую в фикстурную таблицу (без `placeInto()`), затем `Model::orderBy(rank)->pluck(rank)` сравнивается с тем же набором значений, отсортированным в PHP байтовым сравнением (`SORT_STRING`) — вставка в перемешанном порядке, чтобы доказать, что сортирует именно БД, а не порядок вставки
- [x] Тест помечен группой `collation-critical` и на SQLite явно skip'ается с сообщением («SQLite побайтово сравнивает по умолчанию независимо от ветки макроса — не валидирует драйверный синтаксис»), а не молча проходит — то же для теста интроспекции схемы
- [x] Проверка синтаксиса макроса для каждого драйвера: MySQL/MariaDB реально создают колонку с `charset('binary')`, PostgreSQL — с `collation('C')` (интроспекция схемы через `Schema::getColumns()` после миграции, не только косвенно через сортировку)

**Локальная верификация (сверх тикета):** окружение реализации имеет доступ к Docker, но без сети (нет доступа к Docker Hub для новых образов) — образ `postgres:15.5` уже был закеширован локально (используется другими проектами на этой машине), MySQL/MariaDB — нет. Поднял временный контейнер `postgres:15.5` и прогнал **весь набор тестов пакета вживую** против него: без правок он воспроизвёл ту же ошибку `SQLSTATE[42P07]: relation already exists` начиная со второго теста в файле — миграции фикстур создавались в `setUp()` без отката, что работает только с эфемерной `:memory:` sqlite-базой. На постоянном сервере таблицы накапливаются между тестами. Это не гипотетический риск CI — воспроизведено и исправлено до commit, не после первого красного прогона в GitHub Actions.

**Проверка коллации PostgreSQL прошла по-настоящему** (не только компилируется): сгенерированный SQL миграции содержал `"rank" varchar(64) collate "C"`, тест интроспекции схемы и тест сортировки на перемешанных данных оба зелёные против реального Postgres. MySQL/MariaDB-ветки макроса **не проверены локально** — идентичны по форме (`charset('binary')`, тот же `match`-блок), но фактическое подтверждение возможно только в CI, где есть доступ к Docker Hub. Это прямо соответствует смыслу тикета: SQLite декоративен, а полная кросс-драйверная гарантия наступает только когда матрица реально прогонится в GitHub Actions.

**Пост-ревью правка (Standards-ось):** тест сортировки изначально генерировал ранги только последовательными append'ами (монотонно по построению) и перемешивал лишь порядок вставки — реальную нагрузку на побайтовое сравнение (строки разной длины) даёт именно чередование append/prepend, уже используемое в юнит-тесте генератора (тикет 02). Приведено к тому же паттерну и перепроверено вживую на Postgres.
