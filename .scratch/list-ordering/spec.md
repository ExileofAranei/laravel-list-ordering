# laravel-list-ordering: fractional-rank ordering primitive

Status: ready-for-agent

## Problem Statement

Consumers that store an ordered flat list as rows in a database table (a list of tasks in a board column, images in a gallery, blocks in a slot) currently have no reusable, self-contained way to persist that order. The common approach — an integer position column — breaks down in ways that are specific to *this* problem, not to any one consumer:

- Moving one element in a list of twenty rewrites up to nineteen rows the user never touched.
- Two editors acting on overlapping ranges of the same list renumber concurrently and silently drop one of the moves.
- Restoring a soft-deleted element "to its previous place" is meaningless with integer positions, because neighbors may have shifted while the element was gone — the old absolute position no longer means anything.
- Drag-and-drop between two different lists doesn't fit an API built around "move within my own list."

The package needs to solve ordering once, generically, and be provably independent of any consumer's domain — verified by a CI that never sees the consuming project.

## Solution

A Laravel package (`exileofaranei/laravel-list-ordering`) that orders rows within a flat list using string fractional ranks: a lexicographically dense key where a value can always be generated strictly between any two existing values. Insertion and movement touch exactly one row.

The list a row belongs to is defined by an arbitrary set of column values on the model (declared by the model, not hardcoded by the package). Movement — whether within a list or between two different lists — goes through one primitive, expressed entirely in terms of neighbor anchors, never integer positions, so that a future "restore to where it was" feature can reuse it without special-casing.

The package knows nothing about trees, hierarchies, or any consumer's domain vocabulary. It ships as an independently versioned, independently tested Composer package from its own repository.

## User Stories

1. As a package consumer, I want to declare which columns define a model's list membership, so that the package can group rows without me writing any query logic.
2. As a package consumer, I want a list defined by zero columns to mean "one global list," so that flat, ungrouped lists (e.g. landing-page features) work without special-casing.
3. As a package consumer, I want any of the grouping columns to be `null` and have that treated as a real value (`IS NULL`), so that nullable foreign keys don't silently produce an empty or wrong list.
4. As a package consumer, I want one method that both reorders within a list and moves between lists, so that I don't have to maintain two code paths for what is conceptually the same operation.
5. As a package consumer, I want to express the target position purely via the neighbors it should sit between, so that I never touch an integer position in the API.
6. As a package consumer, I want the rank to be regenerated fresh in the context of the destination list when an element moves, so that a rank from list A never leaks meaning into list B.
7. As a package consumer, I want the change of list-membership columns and the new rank written in a single atomic update, so that a row is never observably "in the new list with the old rank."
8. As a package consumer, I want thin, readable wrapper methods (`placeAtEnd`, `placeAtStart`, `placeAfter`, `placeBefore`) over the one primitive, so that call sites communicate intent instead of `placeInto($group, null, null)`.
9. As a package consumer, I want inserting a brand-new (not-yet-persisted) model into a list to compute its rank and insert it in one `save()`, so that there's never an intermediate row with a missing/wrong rank.
10. As a package consumer, I want to pass only one neighbor (e.g. "after X") and have the package resolve the other bound automatically, so that I don't have to fetch and pass both neighbors for a common insertion.
11. As a package consumer restoring a soft-deleted element, I want to say "place after X" even if X has since moved to a different list, and have the element land in X's *current* list, so that restore-by-anchor stays correct without me tracking X's history.
12. As a package consumer restoring a soft-deleted element, I want to say "place before Y" when the original neighbor no longer exists, so that restore degrades gracefully to whatever neighbor is still known.
13. As a package consumer restoring a soft-deleted element, I want to call the primitive with no known anchors at all and have it land at the end of the target list without erroring, so that a total loss of context still produces a sane, non-crashing outcome.
14. As a package consumer, I want passing an anchor that doesn't actually belong to the target group to raise a clear exception, so that a wrong call site fails loudly instead of producing a rank that doesn't belong where I think it does.
15. As a package consumer, I want two explicitly-passed anchors to be used purely as bounds (not validated for adjacency), so that restoring "between X and Y" still works correctly even if other elements were inserted between them in the meantime.
16. As a package consumer, I want a direct write to the list-membership or rank columns on an already-persisted row (bypassing the primitive) to throw, so that I get an early, loud signal instead of a silently corrupted list.
17. As a package consumer, I want that guard to not interfere with `create()`, factories, or seeders setting an initial rank directly, so that I can set up known list state without an artificial backdoor in the contract.
18. As a package consumer, I want the ordering guard's limits documented plainly (it does not see `insert()`, `upsert()`, or `withoutEvents()`; the real integrity guarantee is the DB unique index), so that I don't overestimate what the guard protects.
19. As a package consumer, I want a `scopeOrdered()` on the model, so that fetching a list in order doesn't require every consumer to hand-write `orderBy('rank')` and remember to also filter by group.
20. As a package consumer, I want the DB sort order of the rank column to exactly match PHP's byte-wise string sort order, so that "the database's idea of order" and "the application's idea of order" never diverge.
21. As a package consumer, I want a Blueprint macro that creates the rank column with the correct byte-comparable collation per driver, so that I can't forget to configure this correctly when writing my own migration.
22. As a package consumer, I want the composite unique index (group columns + rank) enforced at the DB level, so that a concurrent write can never park two rows on the same rank even if the guard is bypassed.
23. As a package consumer, I want a rank conflict from a concurrent insert to trigger an automatic retry with fresh neighbor resolution (not a crash), so that ordinary concurrent use doesn't surface a raw database exception.
24. As a package consumer, I want an artisan command to check whether a model's declared list columns match its actual DB unique index, so that I can catch drift between the model and a migration written by hand, on my own schedule (in CI or manually), not as a surprise at request time.
25. As a package consumer, I want a matching test assertion (`assertOrderingIndexMatches`) usable from my own test suite, so that I can enforce that check continuously without depending on the package's runtime behavior.
26. As a package maintainer, I want exactly one abstract method in the public contract (`orderingGroupColumns()`), so that any second abstract method is an immediate signal that consumer domain logic has leaked into the package.
27. As a package maintainer, I want the package's own source and tests to contain zero domain vocabulary belonging to any consumer (block, canvas, slot, tree, node, parent, child, category, article, news, etc.), enforced by a `grep` gate in CI, so that independence isn't just a design intention but a mechanically checked fact.
28. As a package maintainer, I want the package's tests to run against fixture models from an intentionally unrelated domain, using `orchestra/testbench`, in a CI that has no access to any consuming project, so that "tests are green" means "works standalone," not "works alongside a specific app."
29. As a package maintainer, I want the rank-generation algorithm isolated behind a `RankGenerator` interface with one default implementation, so that swapping the algorithm later is a container binding change, not an API change.
30. As a package maintainer, I want the package's own exceptions and events (not reused from elsewhere), so that consumers can catch/listen for package-specific conditions without coupling to internals.
31. As a developer implementing this package, I want the model to implement `Orderable` and `use HasOrdering` and have the trait satisfy the full contract except the one abstract method, so that `instanceof Orderable` is actually useful for static analysis (it guarantees the whole primitive, not just the group-columns declaration).
32. As a developer implementing this package, I want a test proving that after any placement operation, the ranks of every untouched row in the affected list(s) are byte-identical to their pre-operation values, so that "moves exactly one row" is a verified invariant, not just a design claim.
33. As a developer implementing this package, I want a test proving `Positioned::$from` and `Positioned::$to` differ correctly on a cross-list move (i.e. `currentGroupKey()` reads pre-mutation state), so that a naive implementation that reads already-mutated in-memory attributes is caught immediately.
34. As a developer implementing this package, I want `scopeOrdered()` used without a `GroupKey` documented and tested to only guarantee correct order *within* each group present in the result set, not a global order across groups, so that nobody mistakes "compiles and returns rows" for "returns them correctly ordered."

## Implementation Decisions

**Package identity.** Composer name `exileofaranei/laravel-list-ordering`, namespace `ExileOfAranei\ListOrdering\`, MIT license with the individual author as copyright holder (year included), own repository from the first commit, Laravel package-tools-based service provider registered via Laravel package auto-discovery. Allowed dependencies: PHP, `illuminate/database`, `illuminate/support`, `illuminate/contracts`, `spatie/laravel-package-tools`. No dependency on any application or organization package. `php: ^8.3` (matches the actual floor imposed by `orchestra/testbench` under Laravel 13, not an arbitrarily chosen minimum).

**Public contract (`Contracts\Orderable`).** Declares the full public surface a caller can rely on through the interface type, not just the one method the model authors:
- `orderingGroupColumns(): array` — the one abstract method a model must write.
- `currentGroupKey(): GroupKey`
- `orderingRankColumn(): string`
- `placeInto(GroupKey $group, ?Orderable $after, ?Orderable $before): void`

This is deliberate: `instanceof Orderable` must be enough for static analysis to know the primitive exists, not just that the model declared group columns. The single-abstract-method rule (§3.1 of the originating spec) governs how many methods a *model* is forced to write, not how many methods the *interface* declares — the trait supplies the other three.

**Ordering trait (`Concerns\HasOrdering`).** Named without repeating the package name (`HasOrdering`, not `HasListOrdering` — the namespace already says which package it's from) and without reading as a predicate (`HasOrdering`, not `IsOrderable` — it grants a capability, and `implements Orderable { use HasOrdering; }` reads as a sentence rather than a tautology). Declares `orderingGroupColumns()` abstract again inside the trait itself, so a model that uses the trait without the interface fails to compile — this is the trait's half of enforcing §3.1.

Implements:
- `currentGroupKey()` — builds a `GroupKey` from the model's declared columns' **original** (pre-mutation) attribute values (`getOriginal()`), not in-memory-dirty values. This matters specifically for the `Positioned` event: after `placeInto()` has written new group-column values into memory but before `save()` commits, `currentGroupKey()` must still report the *old* group, or `Positioned::$from` and `$to` collapse to the same value on every cross-list move.
- `orderingRankColumn(): string` — returns `'rank'` by default; overridden by ordinary method overriding in the consuming model, not by a protected property. (A property and a method sharing the name `orderingRankColumn` was considered and rejected — legal in PHP but reads as a mistake and produces duplicate IDE autocomplete entries.)
- `placeInto(GroupKey $group, ?Orderable $after, ?Orderable $before): void` — the one primitive; delegates to the internal `Positioner`. Works identically whether the model is new (`exists === false`, computes the rank and inserts in one `save()`) or already persisted (`exists === true`, moves it). Anchors define bounds, not required adjacency: if other rows already sit between the two passed anchors, the new rank is still generated strictly between the bounds — this is required for the restore-from-trash use case, where the anchors were adjacent at delete time but may not be anymore.
- Thin wrappers, **not** part of the `Orderable` contract (deliberately — adding a method to an interface later is a breaking change for anyone implementing it directly; removing one from a trait is not, so wrappers stay unproven until they've settled): `placeAtEnd(GroupKey $group)`, `placeAtStart(GroupKey $group)`, `placeAfter(Model&Orderable $anchor)`, `placeBefore(Model&Orderable $anchor)`. The latter two take `Model&Orderable`, not `self&Orderable` — `self`/`static`/`parent` are illegal in PHP intersection types (hard compile error), and semantically an anchor may legitimately be a different class under single-table inheritance.
  - `placeAfter($anchor)` / `placeBefore($anchor)` resolve the target group from `$anchor->currentGroupKey()` — the anchor's group at call time, not any group the caller might otherwise assume. This is what makes user story 11 (anchor moved lists since it was recorded) work with no special API.
- `scopeOrdered(Builder $query, ?GroupKey $group = null): Builder` — applies `$group->applyTo()` when given, always applies `orderBy(rank)`. When `$group` is omitted, the scope **only sorts** and assumes the query is already narrowed to a single list (e.g. via an already-scoped relationship); it does not, and cannot, guarantee cross-group order. This must be stated in the method's PHPDoc, not left implicit.
- `bootHasOrdering()` — registers a `saving` guard: if the model `exists === true` and any of the group columns or the rank column are dirty without the trait's own internal bypass flag set, throw `GuardedColumnMutationException`. The bypass flag is set by `Positioner` immediately before its own `save()` call and cleared in a `finally` block, so an exception mid-`placeInto()` can never leave the model permanently unguarded. The guard does not fire on `insert()`, `upsert()`, or any write path that bypasses Eloquent's `saving` event (including `withoutEvents()`) — this is a known, documented limitation, not a gap to close on this pass. The actual integrity guarantee against corruption is the DB-level composite unique index; the guard is a developer-experience convenience layered on top, and the README must say so plainly rather than implying stronger protection than it has.

**`Support\GroupKey`** (value object). Constructed via `GroupKey::of(array $columns)` from raw column-name-to-value pairs (needed because the target group in a cross-list move may not correspond to any currently-loaded model to read columns from). `applyTo(Builder $query): Builder` applies the group as query constraints, using `whereNull()` for any column whose value is `null` — the one place in the package this branch exists, so it isn't reimplemented ad hoc at every call site and silently mishandled. `equals(GroupKey $other): bool` compares column sets independent of array order. `placeInto()` validates that the column *names* of a passed `GroupKey` exactly match `orderingGroupColumns()`, throwing `InvalidGroupKeyException` on mismatch (catches a typo'd column name before it silently creates a phantom group).

**`Contracts\RankGenerator`** / **`Generators\FractionalRankGenerator`.** `RankGenerator::between(?string $lower, ?string $upper): string` generates a rank strictly between two optional bounds (either or both `null` meaning unbounded on that side). Bound behind an interface with exactly one default implementation so that swapping the algorithm is a container-binding change, never an API change. Default implementation uses a byte-sortable ASCII alphabet (`0-9A-Za-z`, whose codepoint order matches its intended sort order) so DB byte comparison and PHP string comparison agree by construction.

**Internal `Positioner`.** Not part of the public contract; the only class allowed to bypass the ordering guard, and the one place `?Orderable` parameters are narrowed to `Model&Orderable` — done via an explicit `throw`, never `assert()` (production commonly runs with `zend.assertions=-1`, under which `assert()` compiles to nothing — a silent no-op narrowing would let a non-`Model` `Orderable` reach `getOriginal()`/`save()` uncaught). Signature uses DNF types for the nullable intersection parameters, which PHP 8.2+ requires parenthesized: `(Model&Orderable)|null`.

Anchor resolution rules for `place()` (this is the resolved semantics for "what happens when an anchor is omitted," worked out because the originating requirements didn't fully specify it and a silent choice here would have shaped the whole API):
- Both anchors given explicitly → used as bounds as-is (no adjacency check — see the restore-from-trash rationale above). Each is validated to belong to the target `GroupKey` (via its own `currentGroupKey()`); mismatch throws `InvalidAnchorException`.
- Only `$after` given → `$before` is resolved automatically as the next row after `$after` in the target group (or none, if `$after` is last).
- Only `$before` given → `$after` is resolved automatically as the row immediately preceding `$before` in the target group (or none, if `$before` is first).
- Neither given → treated as "place at the end of the target group": `$after` is resolved as the group's current last row (`ORDER BY rank DESC LIMIT 1`), `$before` stays `null`. If the group is empty, both remain `null` and the generator's seed value is used. This makes `placeInto()` total — it never throws purely for lack of anchors — which is required for the trash-restore case where no anchor may still exist.
- On a unique-constraint conflict during the write (a concurrent insert took the same gap), retry up to a small fixed limit (constructor parameter on `Positioner`, default 3, not a published config value — see below). **Each retry re-resolves anchors from the database from scratch**, not just regenerates a rank between the same previously-computed bounds — reusing stale bounds would deterministically reproduce the same conflict, since the concurrent writer occupies exactly that gap. This is a correctness requirement for convergence, not a performance tweak, and it must be a distinct, explicit line item in the implementation ticket — it isn't derivable from the public API surface alone.
- After a successful write, dispatch `Events\Positioned` carrying the model, the pre-mutation `GroupKey` (from `currentGroupKey()`, read *before* mutation — see the trait notes above), and the target `GroupKey`.

**Schema / migration support.** A `Blueprint::orderingRank(string $column = 'rank')` macro registered by the service provider, generic across models (it has no knowledge of any specific model's columns). Creates a 64-character column (not 255 — `utf8mb4_bin` at 255 chars is 1020 bytes in an InnoDB index key; combined with even two string group columns this risks exceeding InnoDB's 3072-byte index key budget, and 64 base62 characters is far more headroom than any realistic rank will need before a future rebalance would be warranted anyway) with driver-specific byte-comparable collation: MySQL/MariaDB use `charset('binary')`, PostgreSQL uses `collation('C')`, SQLite gets no explicit collation call (already byte-comparable by default, and passing an explicit `null` collation risks malformed SQL rather than "no-op"). Consumers still write their own migration and their own composite unique index (group columns + rank column) — the package cannot generate that index automatically because migrations are immutable historical snapshots and a model's declared columns can change over time, which would make an auto-generated index silently different for the same migration file at different points in time.

**Index-drift detection.** Not a lazy runtime check (would introduce unexpected request-time latency and an unrecoverable-at-runtime failure mode). Instead: an artisan command (`list-ordering:check-index {model?} {--all}`) the consumer runs on their own schedule (CI, manually), plus a matching test-assertion trait (`Testing\AssertsOrderingIndex::assertOrderingIndexMatches(string $modelClass)`) the consumer can wire into their own test suite. Both read the expected column set from `orderingGroupColumns()` + `orderingRankColumn()` and compare against the actual DB index via the driver's schema introspection.

**No config file.** The one tunable value in scope (`Positioner`'s max retry count) is a constructor parameter with a hardcoded default (3), overridden via container binding if ever needed — not a published config file, `vendor:publish` tag, and README section for a single integer. A config file gets introduced only once there are enough settings to justify one.

**Timestamps.** `placeInto()` touches `updated_at` like any other `save()` — no special-casing, no config flag. A consumer who wants different behavior has Laravel's own `withoutTimestamps()` available.

**Cleanup of inherited skeleton.** The `Facade`, `Skeleton`-derived command stub, and `config/list-ordering.php` publishing inherited from the Spatie package skeleton are removed — none are called for by any requirement, and the facade in particular adds public surface area that doesn't fit "one primitive."

## Testing Decisions

Primary seam: fixture Eloquent models exercising the **public trait API** (`placeInto()` and its wrappers, `scopeOrdered()`, the `saving` guard) against a real database via `orchestra/testbench`. Fixture models belong to an intentionally unrelated domain (not the kanban/gallery/landing examples used for illustration elsewhere in this spec, to avoid conflating documentation examples with test fixtures), and no models from any consuming application are ever referenced — this is what makes "tests are green in the package's own CI" mean "works standalone."

`Positioner` is not tested directly (per discussion) — every behavior it implements is observable and tested through the model's public API. Narrow, model-independent unit tests are reserved for logic that genuinely can't be observed that way:
- `FractionalRankGenerator::between()` — result is always strictly between the given bounds under byte-wise comparison, is deterministic, and its length growth under repeated same-boundary insertion is bounded and understood (informs §9.5's documented — not implemented — rebalancing concern).
- `GroupKey` — `equals()` is order-independent; `applyTo()` correctly uses `whereNull()` for `null`-valued columns; construction against a mismatched column set is caught by `placeInto()`'s validation (tested at the model level, since that's where the exception is actually thrown).

Feature-level coverage (all through fixture models, all through the public trait API):
- The three grouping shapes from the originating requirements: a composite non-null key (two columns), a single-column key, and the empty-array "one global list" case — proving none of them require special-casing anywhere in the API.
- All eight anchor-resolution scenarios discussed: empty-list insert, insert between neighbors, in-list reorder, cross-list move between two elements, cross-list move into an empty list, "after X" where X has since changed groups, "after X" where X no longer exists but its former neighbor does, and no known anchor at all.
- **Untouched-row invariant**: build a list of N rows, snapshot every rank except the one being moved, perform a placement, re-fetch by the same IDs, and assert the snapshot is byte-identical (`assertSame`, not a count-based diff — this catches both "a neighbor's rank changed" and "row order changed without any rank value changing").
- **`Positioned` event correctness**: a cross-list move must produce a `Positioned` event whose `$from` and `$to` differ — this specifically catches a `currentGroupKey()` implementation that reads already-mutated in-memory attributes instead of `getOriginal()`.
- **Guard behavior**: a direct attribute write + `save()` on an already-persisted row throws `GuardedColumnMutationException`; the same write path taken through `placeInto()` does not throw; `create()` / factory-based fixture setup with an explicit rank does not throw (this is the resolved reading of "guard active only when `exists === true`").
- **Anchor-validity**: an anchor that does not belong to the passed target `GroupKey` throws `InvalidAnchorException`.
- **Non-adjacent anchors**: two explicitly-passed anchors with other rows already between them still produce a valid rank strictly between the two bounds (restore-from-trash correctness).
- **`scopeOrdered()` without a group**: two independent lists in the same table, `Model::ordered()` with no `GroupKey` — assert order is correct *within* each list; assert nothing about relative order *between* lists (only that it doesn't error or silently interleave in a way that breaks the within-list guarantee).
- **DB sort order vs. PHP sort order**: insert a set of ranks via the generator, compare `Model::orderBy(rank)->pluck(rank)` against the same values sorted in PHP by byte comparison (`strcmp`/`SORT_STRING`) — run under SQLite always, and under MySQL/MariaDB/PostgreSQL via CI service containers (SQLite alone doesn't validate this: it's byte-comparable by default regardless of what the driver-specific collation macro branch actually does, so a SQLite-only pass is decorative for this specific concern and must not be treated as covering it).
- **Concurrency / retry convergence**: force a unique-constraint conflict on the first attempt (e.g. a test double / pre-seeded conflicting rank) and assert the operation still succeeds via retry, and that the retry re-resolved neighbors rather than reusing the original (failed) bounds.

CI gates (mechanical, not Pest tests): grep for `App\` in `src/`+`tests/` (fails if found), grep for the banned consumer-domain vocabulary list (fails if found), `composer test` run with no consuming project present. All three are required for "done," per the originating requirement that CI without access to the consumer is the actual proof of independence.

Prior art in this repo: none yet — this is the package's first real feature. Test scaffolding (`tests/Pest.php`, `tests/TestCase.php`, `orchestra/testbench` wiring) already exists from the Spatie skeleton and is reused as-is.

## Out of Scope

- Drag-and-drop UI integration in any consuming project.
- Integration into the actual consuming project (the block-content editor), including migrating existing integer-position data to ranks.
- Implementing rank rebalancing (only: not closing off the ability to add it later — rank length and column sizing are chosen with this in mind, no rebalancing mechanism is built).
- Nested sets, trees, hierarchies, or any abstraction over them, in any form.
- Any of the anti-patterns explicitly ruled out: `moveUp()`/`moveDown()`/`moveToPosition(int)`/`setNewOrder(array)`, a separate "move to another list" method distinct from the reorder method, an integer position column in any role (including auxiliary), renumbering neighbors on insert.
- A config file / `vendor:publish`-able settings for the retry count or any other single tunable.
- Extending the CI dependency-boundary check beyond `grep` (e.g. `deptrac`, `phpat`) — noted as a possible future strengthening, not required for this pass.

## Further Notes

- This spec's decisions were reached through an extended design discussion (not a single interview pass) that resolved several genuine gaps left open by the originating requirements document — most importantly: the guard's scope relative to model creation vs. update, the full anchor-resolution semantics for `placeInto()` (including the "neither anchor given" case), and the choice to widen the public `Orderable` contract beyond the single required abstract method. These are documented above as implementation decisions precisely so a future reader doesn't mistake them for having been dictated by the original requirements — they were derived, and flagged as such at the time, per the instruction not to resolve conflicts silently.
- PHP language constraints surfaced during design and are reflected directly in the signatures above, not left as "to be discovered during implementation": `self`/`static`/`parent` are illegal in intersection types; nullable intersection types require parenthesized DNF syntax (`(A&B)|null`) rather than `?A&B`.
- The retry-must-re-resolve-anchors requirement and the guard's `finally`-based cleanup are both called out explicitly because neither is derivable by reading the public API surface alone — they need to appear as their own checklist items in whatever ticket(s) implement `Positioner`, or a correct-looking implementation can still ship the wrong behavior.
